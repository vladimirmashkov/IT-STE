# Хранение стандартов

[English](storage.md)

## 1. Независимые координаты

| Координата | Значение |
| --- | --- |
| `standard` | `asd-ste100` или `it-ste`; пространства имён не смешиваются |
| `version` | Точное обозначение редакции ASD-STE100 либо SemVer-версия IT-STE |
| `revision` | Снимок представления этой версии: `r0001`, `r0002`, … |
| `language` | Языковой тег BCP 47 отдельной записи, например `en` или `ru` |

Редакция исходного стандарта не меняется из-за нового перевода, исправления извлечения текста или метаданных: для этого выпускается новая `revision`. Изменение первичного нормативного текста IT-STE требует новой `version`.

Английский (`en`) — основной и нормативный язык. Русский (`ru`) — предпочтительный второй язык, но он и все остальные переводы опциональны. Значение `primary_language` — `en`; `languages` перечисляет только языки, представленные в снимке. См. [языковую политику](language-policy.ru.md).

В `catalog.json` перечисляются опубликованные снимки. Элемент `releases` содержит `version`, `revision` и путь `manifest` относительно корня репозитория. Начальные списки пусты: номера реальных редакций ASD-STE100 и версии IT-STE ещё не зарегистрированы.

## 2. Каталог одного снимка

Схема ниже описывает будущие каталоги, а не уже опубликованную редакцию:

```text
standards/<standard>/versions/<version>/revisions/<revision>/
  manifest.json
  sources/
    <source-id>.json
  content/
    en/
      rules/<id>.json
      terms/<id>.json
    ru/
      rules/<id>.json
      terms/<id>.json
    <other-bcp47-tag>/
      rules/<id>.json
      terms/<id>.json
  relations.jsonl
```

`manifest.json` явно перечисляет файлы записей и метаданных источников в массивах `records` и `sources`. Поле `relations` содержит путь к JSONL-файлу связей либо `null`. Все эти пути относительны каталогу манифеста; выход за его пределы запрещён. Присутствие файла в каталоге само по себе не включает его в корпус.

Другие поля манифеста: `schema_version`, `standard`, `version`, `revision`, `status`, `primary_language`, `languages`, `language_coverage`, `supersedes`, `released_at`. `languages` перечисляет только реально представленные языки. `language_coverage` сопоставляет каждому языку полноту `partial` или `complete`. `supersedes` — ссылка `{standard, version, revision}` на предыдущий снимок либо `null`.

Для опубликованного снимка IT-STE в списке должен присутствовать `en`, а `language_coverage.en` должен быть равен `complete`. Дополнительные языки могут отсутствовать или быть частичными. Ключи `language_coverage` должны в точности совпадать с `languages`.

`schema_version` — версия формата данных, а не стандарта. Изменение несовместимого формата требует новой major-версии схемы. Общий формат описан документами и шаблонами; исполняемых JSON Schema ещё нет. Узкий [канонический draft-пилот](it-ste-canonical-pilot.ru.md) добавляет профиль `it-ste-pilot-v1` формата `1.1.0` с исполняемым валидатором на стандартной библиотеке, структурными координатами источника и смысловых аспектов, а также сегментами прозы и литералов в примерах. Общие проверки релиза и переводов он не реализует.

## 3. Канонические записи

Один UTF-8 JSON-файл хранит одно правило или один смысл термина на одном языке. Не ведём параллельно редактируемую Markdown-копию. Общие поля показаны в [шаблоне правила](../templates/rule.json) и [шаблоне термина](../templates/term.json).

- `id` — стабильный идентификатор, например `ITSTE-R-0001` или `ITSTE-T-0001`. Его не переиспользуют для другой сущности. Префиксы `ITSTE` и `ASDSTE` различают наши пространства имён; это не официальная нумерация ASD.
- `kind` — `rule` или `term`. Термин с другим смыслом получает другой ID, даже если написание совпадает.
- `language` — язык записи. Перевод сохраняет ID исходной сущности.
- `status` — `draft`, `review`, `approved` или `withdrawn`.
- `origin` — `original`, `upstream`, `adaptation` или `translation`.
- `source_refs` — ссылки `{source_id, locator}` на метаданные источника и точное место в нём: правило, раздел или страницу.
- `rights` — лицензия и её URL, права на распространение и адаптацию, атрибуция и основания этих прав. Лицензия не выводится автоматически из имени каталога.

Для правила отдельно хранятся `title`, нормативный `text`, область применения `applies_to` и положительные/отрицательные `examples`. Для термина — `term`, `part_of_speech`, `definition`, `usage`, `alternatives`, `examples`. `usage`: `allowed`, `restricted` или `prohibited`; `alternatives` — ID терминов того же снимка и языка.

Ссылка на запись всегда содержит все координаты:

```json
{
  "standard": "it-ste",
  "version": "0.1.0",
  "revision": "r0001",
  "language": "en",
  "kind": "rule",
  "id": "ITSTE-R-0001"
}
```

Это иллюстрация адреса, не объявление существующего релиза. Ключ записи для индекса строится как `standard@version#revision/language/kind/id`. Голый ID не определяет версию и не годится как уникальный ключ LLM-индекса.

## 4. Перевод — не адаптация

`translation_of` у перевода содержит `ref` с полным адресом исходной записи и `source_sha256` — SHA-256 байтов её канонического файла. У исходной записи на основном языке поле равно `null`.

После изменения источника перевод требует повторной проверки; старый хеш нельзя молча заменять новым. Ссылка закрепляется за конкретной ревизией, а не за `latest`. Заимствованные примеры, ограничения и смысл должны оставаться различимыми.

Адаптация IT-STE получает собственный ID и `origin: adaptation`: она не выдаётся за перевод ASD-STE100. Связь хранится в `relations.jsonl`:

- `adapted_from` — производная запись → запись-источник; `rationale` объясняет сохранённое и изменённое;
- `replaces` — новая сущность → заменённая;
- `related_to` — другая явно обоснованная связь.

У связи есть `schema_version`, `relation`, `from`, `to`, `rationale`. Обе стороны — полные адреса записей. Несколько строк поддерживают связи многие-ко-многим. Если текст исходной записи нельзя хранить, используйте `source_refs` с локатором внешнего источника, а не ссылку на несуществующую запись.

## 5. Источники и права

[Шаблон источника](../templates/source.json) хранит название, стандарт и редакцию, URL, дату получения, SHA-256 исходного артефакта и сведения о правах. Неизвестные сведения обозначаются `null`, а не вымышленным номером или датой.

В `rights`:

- `license` — SPDX ID либо документированный `LicenseRef-…`; `license_url` — ссылка на условия;
- `redistribution` и `adaptation` — `allowed`, `forbidden` или `unknown`;
- `attribution` — массив предоставленных имён/обозначений авторства и URL;
- `evidence` — публичные URL или пути от корня репозитория к основаниям прав, без секретов и непубличной переписки.

`allowed` означает проверенное разрешение **на условиях указанной лицензии**, а не отсутствие ограничений. `unknown` не является разрешением. Для чужого текста, его извлечения или перевода проверяются права на распространение и соответствующее использование; наша лицензия не подставляется вместо лицензии источника. Для перевода или адаптации проверяются также права на создание производного материала.

До проверки прав храним только библиографические метаданные и собственные описания, без защищённого текста и примеров. Бесплатное получение PDF само по себе не даёт права публиковать его или перевод. Ссылки на источники и обсуждение общих принципов не равнозначны перепубликации текста стандарта.

Локальные исходные артефакты размещаются в `.local/sources/`, исключённом из Git. Это защита от случайного коммита, а не разрешение на использование. Публикация исходных артефактов требует отдельной проверки прав; публичный корпус не зависит от наличия локального PDF.

## 6. Жизненный цикл

1. Скопировать [шаблон манифеста](../templates/manifest.json) в каталог новой версии/ревизии со статусом `draft`.
2. Заполнить источники, записи, языки, полноту переводов и права. Удалить `template: true` только после заполнения: шаблоны не являются содержимым стандарта.
3. Сначала создать и утвердить английские исходные записи. Опубликованный нормативный набор IT-STE требует полного английского покрытия; русский и другие переводы могут появиться в следующих ревизиях.
4. Проверить уникальность адресов, существование всех ссылок, совпадение языка и ID с путями, хеши источников перевода и права. Переводы и адаптации проходят отдельную проверку смысла.
5. Присвоить записям `approved` либо `withdrawn`. В опубликованном снимке не должно быть `draft` и `review`.
6. Установить манифесту `status: released`, указать дату `released_at` в ISO 8601, добавить снимок в `catalog.json` и зафиксировать его в Git. Публикуемые выгрузки закреплять за полным commit ID.
7. Опубликованный снимок не перезаписывать: создавать следующую ревизию либо версию. Старые снимки остаются адресуемыми; `supersedes` и `replaces` сохраняют историю.

Файлы JSON/JSONL используют UTF-8 без BOM, LF и завершающий перевод строки. JSONL содержит ровно один объект на строку. Технические поля и ID пишутся по-английски, текст записи — на языке `language`.

## 7. Производные представления

Markdown, JSONL и поисковые индексы не редактируются как независимый стандарт. Они генерируются из явно выбранного опубликованного снимка с сохранением прав и атрибуции. Контракт описан в [llm/README.ru.md](../llm/README.ru.md).

Каталоги `templates/`, `docs/`, локальные исходники и чужие непроверенные тексты не попадают в нормативный LLM-корпус при обходе репозитория. Команда `python3 tools/it_ste_corpus.py check` проверяет только структуру и аутентифицированное происхождение draft-пилота. Общие проверки релиза, соответствия произвольной прозы и экспорт остаются будущей работой; три draft-записи не являются опубликованным нормативным LLM-корпусом.
