External evidence (inspected 2026-10-22):
- [Transmission Control Protocol, RFC 9293, §3.5.1.1](https://www.rfc-editor.org/rfc/rfc9293.html#name-full-duplex); Eddy, IETF, Internet Standards Track, August 2022. TCP supports bidirectional data flow, but an application can send only in one direction. This primary protocol evidence distinguishes simultaneous/possible directionality from the stronger draft requirement for a repeated exchange whose direction changes; it does not define the ASD phrase or every networking protocol.
- [HTTP Semantics, RFC 9110, §§3 and 9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#name-overview); Fielding et al., IETF, Internet Standards Track, June 2022. HTTP has explicit request and response messages, and `CONNECT` describes forwarding data in both directions. This primary protocol evidence supports naming message roles or using `in both directions` when that is the only fact; it is limited to HTTP semantics and does not require the phrase `back and forth`.
- [The WebSocket Protocol, RFC 6455, §1.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-1.1); Fette and Melnikov, IETF, proposed standard, December 2011. WebSocket provides two-way communication in which each side can independently send data, and the specification uses “back and forth” for message transfer. This directly supports retaining the phrase for a bounded endpoint-to-endpoint exchange; its protocol-specific terminology is not a universal permission for vague uses.
- [Clear sentences](https://developers.google.com/tech-writing/one/clear-sentences); Google Technical Writing One, Google Developers, updated 2025-07-07. The guidance recommends precise, strong, specific verbs and warns that generic wording can hide an imprecise or missing actor. This is competent editorial guidance for the clarity restriction, not ASD or networking authority.

Alternatives and decision: Change `D-P173-004` from `needs-review` to `restricted`. Define the draft IT sense as repeatedly exchanging messages or data between two named endpoints, with the direction changing. Keep `in both directions` when only bidirectional flow matters; use `exchange messages between the named endpoints` for a protocol exchange; and use `send the request and receive the response` for request/response behavior. Reject `allowed` because “back and forth” without endpoints or an identified exchange can hide whether a system is copied, migrated, rolled back, or otherwise changed. Reject `prohibited` because WebSocket provides a legitimate bounded two-way message-exchange use and RFC 6455 demonstrates the phrase in that context. The ASD row, protocol facts, and writing guidance are evidence within their stated scopes; the restricted disposition, definition, alternatives, and examples are draft editorial inferences.
