External evidence (inspected 2026-10-22):
- [In case (of)](https://dictionary.cambridge.org/grammar/british-grammar/in-case); English Grammar Today, Cambridge University Press. It distinguishes `if` for a possible or unreal condition from `in case` for preparation, and `in case of + noun` for “if and when something happens”. This is competent linguistic evidence for the alternatives, not an IT standard.
- [If or when?](https://dictionary.cambridge.org/grammar/british-grammar/if-or-when); English Grammar Today, Cambridge University Press. It distinguishes `if` for a possible condition from `when` for a future condition treated as certain, while allowing `if` or `when` for repeated or predictable conditions. This supports the contextual alternative boundary but is not an IT standard.
- [Python Tutorial 4.1, “if Statements”](https://docs.python.org/3/tutorial/controlflow.html#if-statements); Python Software Foundation, Python 3.15.1 documentation, updated 2026-10-22. Alternatives and decision: Change `D-P185-007` from `needs-review` to `restricted`. Define the draft IT sense as introducing a conditional statement for a specified IT condition or event. Retain `if` as the direct source alternative; retain `when the stated condition occurs` only for a condition treated as expected or recurring. Reject unrestricted `allowed` because an unbounded conditional phrase can hide an undefined condition or unsafe response, as in “Restart in case of trouble.” Reject `prohibited` because precise conditional instructions are legitimate in procedures and runbooks, and the source explicitly maps the phrase to `IF`. Do not treat `in case of` as universally wrong: it can be useful for a concise preparedness or emergency notice when the noun and response are explicit.
