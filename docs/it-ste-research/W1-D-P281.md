External evidence:
- “HTTP Semantics,” Roy T. Fielding, Mark Nottingham, and Julian Reschke, RFC 9110, Standards Track, June 2022, https://www.rfc-editor.org/rfc/rfc9110.html, sections 2.4, 5.5, 8.6, 15.5.1, and 15.5.21, accessed 2026-10-23. The specification uses `invalid` for malformed or non-conforming protocol constructs and for values that cannot be processed, while section 8.6 also uses `incorrect` for a known `Content-Length` value that does not match the message. This supports a bounded distinction: `incorrect` can describe an observed mismatch against a stated requirement, but the protocol context and failed condition must be named.
- “Problem Details for HTTP APIs,” Mark Nottingham, Erik Wilde, and Sanjay Dalal, RFC 9457, Standards Track, July 2023, https://www.rfc-editor.org/rfc/rfc9457.html, sections 1, 3, and 3.1.4, accessed 2026-10-23. The standard defines machine-readable details for HTTP errors and says the human-readable `detail` should focus on helping the client correct the specific problem. This supports using `incorrect`/`incorrectly` only with an identifiable value, action, or rule and an actionable correction, not as an unqualified label such as “The server ran incorrectly.”
- “JSON Schema Validation: A Vocabulary for Structural Validation of JSON,” Austin Wright, Henry Andrews, and Ben Hutton, Internet-Draft draft-bhutton-json-schema-validation-01, June 2022, https://json-schema.org/draft/2020-12/json-schema-validation.html, sections 1 and 3, accessed 2026-10-23. It was inspected as a terminology comparison, but it is an expired Internet-Draft and was not treated as controlling evidence; its `valid`/`invalid` vocabulary reinforces the narrower conformance terminology rather than establishing a requirement for these records.

Alternatives and decision: Retain the current definitions and examples. Change both draft dispositions from `needs-review` to `restricted`. For `INCORRECT`, require a named value, state, or rule and an explicit expected comparison; `wrong` is a contextual alternative, while `invalid under the stated rule` is more precise when a formal validity condition is involved. For `INCORRECTLY`, require a named action or process and an observable failed rule or expected behavior; `with the wrong value` and `not as specified` remain contextual alternatives. The ASD row facts, RFC terminology, and RFC 9457 correction-oriented error-detail requirement are sourced; the dispositions and scope limits are editorial inferences. The current problematic examples remain useful boundaries because they omit the object, condition, or observable difference.
