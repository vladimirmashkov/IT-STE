# Инструкции для агентов

[English](AGENTS.md)

Эти инструкции действуют для всего репозитория. Английский документ является основным; русская версия — опциональный перевод.

## Продолжение работы над черновиком IT-STE

Для разбора спорных словарных записей, редакторской проверки и покрытия IT-терминов сначала прочитайте [основной английский handoff](docs/it-ste-draft-handoff.md); доступно [краткое русское резюме](docs/it-ste-draft-handoff.ru.md). Там зафиксированы выполненная работа, три открытые задачи, ограниченная выборка актуальной очереди и проверки. Не загружайте для старта в контекст полный Markdown, все словарные партии или извлечение источника. Пересчитывайте текущие количества: исходные числа в handoff — историческая точка, а не утверждение решений.

Для содержательных решений W1/W2/W3 применяйте согласованный [метод исследования доказательств](docs/it-ste-research-method.md): изучайте компетентные первичные/экспертные источники в интернете, сравнивайте альтернативы и фиксируйте обоснованное черновое решение. Вопросы разметки PDF по-прежнему требуют аутентифицированного PDF. Начинайте с **Current checkpoint** в английском handoff и читайте только заметки активного участка; обновляйте checkpoint после каждого ограниченного этапа. Не перечитывайте всю историю исследований и не заявляйте внешнее подтверждение без изучения источников. Постоянное задание не разрешает утверждение словаря, релиз, staging или коммиты.

## Производный справочник ASD-STE100 Issue 9

Используйте отслеживаемую производную поисковую базу вместо чтения или преобразования всего стандарта:

1. Выполнить `python3 tools/asd_ste100_local.py doctor`, чтобы аутентифицировать опубликованные базу и манифест. Если локальный PDF доступен, дополнительно проверяется его точный SHA-256.
2. Раскрывать контекст постепенно: `overview`; затем `rules` или `search`; затем `rule <ID>`, `excerpt <ID> <QUERY>`, `word <TERM>` или `entry <ID>`. Предпочитать ограниченный `excerpt` и точный `entry`; добавлять `--full`, только если их недостаточно. Использовать `page <PDF_PAGE>` только для проверки указанной страницы. Для экономного машиночитаемого вывода использовать `--compact-json`.
3. Никогда не помещать полное извлечение в контекст. Сохранять версию стандарта и физическую страницу PDF у каждого результата. Считать механически извлечённую структуру непроверенной и сверять неоднозначные формулировки, столбцы, типографику и диаграммы с PDF.
4. Разрешение на публикацию относится к производной базе, но не к исходному PDF. Хранить PDF в `.local/` и никогда не добавлять его в индекс Git, не коммитить и не публиковать. Обновлять опубликованные артефакты только через `build` и `publish`, сохранять сведения о правах ASD и ссылку на IT-STE, не представлять извлечение или адаптацию как официальную рекомендацию ASD.

См. [инструкцию по производному справочнику](docs/asd-ste100-local-reference.ru.md) и [запись о разрешении](docs/permissions/asd-ste100-issue-9-derivatives.ru.md).

## Проверка всех изменений и предложения команд для терминала

После каждого изменения, перед сообщением о завершении:

1. Проверить всё рабочее дерево и индекс командой `git --no-pager --no-optional-locks status --short --untracked-files=all`. Просмотреть незастейдженные и застейдженные изменения командами `git --no-pager diff --find-renames`, `git --no-pager diff --cached --find-renames` и соответствующими вариантами с `--name-status`.
2. Проверить каждое изменение, а не только построчный diff: добавленные, изменённые, удалённые, переименованные или перемещённые и неотслеживаемые файлы, а также изменения типа или режима файла, бинарных файлов и подмодулей, если они есть. Прочитать добавленные и неотслеживаемые файлы, проверить удалённое содержимое через Git и сравнить оба пути переименования, в том числе когда Git показывает удаление и новый неотслеживаемый файл. Если содержимое проверить нельзя, явно сообщить об ограничении.
3. Проанализировать полный набор незакоммиченных изменений: ожидаемое поведение, согласованность, ошибки и случайные или посторонние правки. Отделить свои изменения от уже существующей работы пользователя. Не перезаписывать и не откатывать посторонние изменения. Просмотр изменения не даёт разрешения менять его или включать в предложение коммита.
4. Выполнить подходящие проверки и кратко сообщить полный состав изменений, результаты анализа и валидации. Если проверку выполнить нельзя, объяснить причину.
5. В конце предложить один или несколько коммитов для независимых логических изменений. Для каждого указать точный набор файлов (оба пути для переименований) и очень краткое однострочное сообщение на английском в повелительной форме, желательно не длиннее 50 символов. Указать проверенные изменения, не включённые в предложения, и объяснить причину. Не включать посторонние незакоммиченные изменения без запроса пользователя.
6. Предоставить готовые для копирования команды терминала в блоках `sh` для запуска из корня репозитория, а не только сообщения коммитов. Соблюдать правила безопасности ниже.

### Безопасные предложения команд

- Добавлять в индекс только явно перечисленные проверенные пути через `git add -A -- ...`; учитывать удаления и оба пути переименований. Не использовать общий `git add .` или `git add -A` без путей.
- Ставить `GIT_EDITOR=true` перед командами коммита и передавать предложенное сообщение через `-m`.
- Перед предложением коммита проверить, нет ли посторонних застейдженных изменений. Сохранить их: использовать `git commit --only` с явными путями, только если каждый перечисленный файл целиком относится к предложению. Если в одном файле смешаны посторонние правки, объяснить необходимое выборочное добавление в индекс вместо небезопасного добавления или коммита файла целиком. Не убирать из индекса чужую работу ради удобства команды.

Предложение команд не является разрешением их выполнить. Не добавлять файлы в индекс, не создавать коммиты и не переписывать историю Git без явного запроса пользователя на соответствующее действие.
